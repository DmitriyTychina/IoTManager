# Почему асинхронный веб-сервер в IoTManager — это важно

> Разъяснение (**Explanation**): что даёт перевод прошивки на
> `ASYNC_WEB_SERVER` + `ASYNC_WEB_SOCKETS`, как это работает внутри
> и зачем это обычному разработчителю-домашнему мастеру.
> Аудитория — тот, кто собирает прошивку IoTManager под себя и
> хочет понять, почему «веб всё время подвисает» раньше, а теперь
> — нет.

## Введение: два стиля обслуживания веб-запросов

Любая прошивка, которая показывает веб-интерфейс, должна где-то
принимать HTTP-запросы от браузера и отдавать ответы. В мире
микроконтроллеров это делается двумя способами:

| | Синхронный (`WebServer`) | Асинхронный (`ESPAsyncWebServer`) |
|---|---|---|
| **Как работает** | Обрабатывает один запрос за раз, **блокируя** `loop()`, пока не закончит | Обрабатывает запросы **одновременно**, не блокируя `loop()` |
| **Что происходит с остальной логикой** | Сенсоры, MQTT, сценарии, таймеры — всё **замирают** | Всё работает в фоновом режиме |
| **Клиенты одновременно** | Один | До 5 и более |
| **Память на запрос** | Выделяет буферы на каждый запрос | Использует события и минимум буферов |
| **Прошивка файла по WS** | Блокирует на секунды при потере клиента | Дропает фрейм, закрывает «застрявшего» клиента |

До сентября 2026 IoTManager использовал **синхронный** вариант по
умолчанию. Это значит, что каждая операция веб-интерфейса — запрос к
`/status`, загрузка файла `/config|`, даже просто открытие страницы —
все они **останавливали основной цикл прошивки**. А основной цикл занят
важным: опрос сенсоров, работа MQTT, выполнение сценариев, периодические
задачи. Когда веб-запрос «запирал» цикл на секунду, всё остальное
становилось недоступным.

> 📌 **Главная идея**: асинхронный веб-сервер в IoTManager не просто
> «быстрее» — он **убирает веб-интерфейс из пути** основной логики устройства.

## Почему это важно именно для IoTManager

IoTManager — это не просто «веб-страница на ESP8266». Это система
умного дома, которая одновременно:

1. **Опрашивает сенсоры** — температура, влажность, давление, свет,
   открывающие датчики и т. д. Частота опроса может быть высокой;
2. **Управляет исполнительными устройствами** — реле, сервоприводы,
   шаговые двигатели. Любая задержка в 100–500 мс может быть критична;
3. **Работает с MQTT** — подключение к брокеру, публикация статусов,
   приём команд из мобильного приложения. MQTT-цикл (`mqttLoop()`)
   вызывается в каждом `loop()` и требует регулярного вызова;
4. **Выполняет сценарии** — пользовательская логика в `scenario.txt`,
   которая может содержать задержки, условия, вызовы функций;
5. **Обслуживает веб-интерфейс** — браузер показывает состояние всех
   элементов в реальном времени по веб-сокетам (порт 81).

Все эти задачи работают в одном потоке — `loop()` микроконтроллера.
На ESP32 можно использовать несколько ядер, но логика IoTManager всё
ещё в основном однопоточна: MQTT, сценарии, сенсоры, веб — всё
переплетено в один цикл.

Если веб-сервер **блокирует** цикл, то:

- Сенсоры не опрашиваются, пока пользователь листает страницу;
- MQTT-соединение может пропасть (брокер считает клиент мертвым,
  если нет `ping`/`pong` вовремя);
- Сценарии с задержками «залипают» на секунды;
- Веб-интерфейс перестаёт отвечать на команды.

Это особенно заметно при **многих устройствах на одной странице**
(фича IoTManager позволяет видеть все устройства в одном браузере) —
панель одновременно открывает веб-сокеты к каждому устройству, и каждый
из них может посылать запросы.

## Что конкретно делает асинхронный вариант в IoTManager

Асинхронный веб-сервер в IoTManager построен на двух библиотеках:

| Библиотека | Платформа | Назначение |
|---|---|---|
| `ESP32Async/ESPAsyncWebServer` | ESP8266, ESP32 | Асинхронный HTTP-сервер |
| `ESP32Async/ESPAsyncTCP` | ESP8266 | Асинхронный TCP (зависимость для ESP8266) |
| `AsyncTCP` | ESP32 | Асинхронный TCP (зависимость ESPAsyncWebServer на ESP32) |

Эти библиотеки используют **неблокирующее I/O**: сервер не дожидается,
пока клиент примет данные, а сразу возвращает управление `loop()`.
Все операции с сетью выполняются через **прерывания** и **коллбэки** —
это и есть «асинхронность».

### Как это работает на практике

Когда браузер открывает страницу или посылает команду по веб-сокету,
происходит следующее:

1. **HTTP-запрос** (`/` или `/status`): `ESPAsyncWebServer` принимает
   запрос в прерывании, передаёт его в обработчик через **compatibility-слой**
   (`AsyncWebServerCompat`), и `loop()` сразу продолжает работу.
   Обработчик (`StandWebServer.cpp`) работает с объектом `HTTP`, который
   в асинхронном режиме — это обёртка, а в синхронном — настоящий `WebServer`.
   Один и тот же код обрабатывает оба варианта.

2. **WebSocket-сообщение** (`/pi|`, `/|`, `/devlist|` и т. д.):
   сообщение приходит в коллбэк `onWsEvent`, который **не блокирует**
   `loop()`. Вместо этого сообщение кладётся в **очередь** (8 элементов)
   и обрабатывается позже в `asyncWebSocketsLoop()` — уже в контексте
   `loop()`. Это важно: на ESP32 коллбэк AsyncTCP работает в отдельной
   задаче (FreeRTOS Task), и блокировать её нельзя.

3. **Отправка файла по WS** (например, `/config|` → `config.json`):
   файл читается из LittleFS и отправляется **по частям** — по
   RFC 6455 фреймам по 1024 байта. Сервер не собирает весь файл в
   память, а отправляет фрейм за фреймом. Если клиент «застрял»
   (потерял WiFi, TCP-окно не освобождается), фрейм **дропается**
   в течение 100 мс (для мелких файлов) или 200 мс (для больших),
   а клиент автоматически закрывается через 2 секунды. Раньше же
   (в синхронном варианте) отправка файла могла **заморозить
   `loop()` на 3 секунды**, если клиент терял соединение.

> 💡 Пример: вы открываете IoTManager в браузере, и панель
> сразу запрашивает `layout.json`, `config.json`, `items.json`.
> В асинхронном режиме все эти файлы разбиваются на 1 КБ-фреймы и
> уходят параллельно с опросом сенсоров и работой MQTT. Никто никого
> не ждёт.

### Управление «застрявшими» клиентами

Это одна из ключевых фич асинхронного варианта. Когда клиент
(например, браузер на мобильном телефоне) теряет WiFi, его TCP-окно
перестаёт освобождаться — сервер больше не может отправить данные.
В синхронном режиме это приводило к **синхронному ожиданию 3 секунд**
(`ASYNC_WEB_SOCKETS_SEND_TIMEOUT` / старый таймаут 3000 мс),
в течение которого:

- `loop()` был заморожен;
- сценарии не выполнялись;
- MQTT не получал `ping`/`pong`;
- другие WS-клиенты ждали своей очереди.

В асинхронном режиме каждый фрейм получает **короткий бюджет
времени** (100 мс для мелких, 200 мс для больших файлов). Если
окно TCP не освобождается в течение бюджета — фрейм дропается,
клиент помечается как «застрявший», и через 2 секунды его соединение
автоматически закрывается. При этом:

- если клиент продолжает посылать данные (например, пинги `/pi|`) —
  он считается живым, и «застревание» сбрасывается;
- если данных нет — предполагается, что клиент действительно
  отвалился, и соединение закрывается.

Это устраняет классическую проблему: **«залипает весь UI, когда
открыто несколько вкладок или одна вкладка в фоне»**.

## Порты и протокол: совместимость гарантирована

Асинхронный и синхронный варианты используют **одинаковые порты** и
**одинаковый протокол**:

| Протокол | Порт | Примечание |
|---|---|---|
| HTTP | 80 | Веб-интерфейс |
| WebSocket | 81 | Управление в реальном времени |

WS-команды имеют одинаковый формат в обоих вариантах: `xxxxxx|0012|` —
6 символов заголовка, 4 цифры длины, `|` разделитель. Например:

- `/pi|` — пинг (интерфейс жив);
- `/|` — запрос `layout.json` (всё дашборд);
- `/config|` — запрос `config.json`;
- `/devlis|` — запрос `devlist.json`;
- `/gifnoc|` — запись обратного `config.json`;
- `/sgnittes|` — запись обратного `settings.json`;
- `/tuoal|` — запись обратного `layout.json`;
- `/tsil|` — запись обратного `devlist.json`.

Это значит: **веб-интерфейс (Svelte-приложение в `data_svelte/`) не
меняется ни при переключении между вариантами, ни при смене платы**.
Браузер открывает `ws://<ip>:81` — и всё работает одинаково.

### Compatibility-слой: как один код работает с двумя серверами

Чтобы не писать обработчики дважды, проект использует класс
`AsyncWebServerCompat` (файл `include/WebServerCompat.h`). Он **повторяет
интерфейс синхронного сервера**: `HTTP.on()`, `HTTP.send()`, `HTTP.arg()`,
`HTTP.upload()`, `HTTP.serveStatic()` и т. д.

В синхронном режиме `HTTP` — это настоящий `WebServer` (ESP32) или
`ESP8266WebServer` (ESP8266). В асинхронном режиме `HTTP` — объект
`AsyncWebServerCompat`, который:

- Привязывает текущий `AsyncWebServerRequest*` при входящем запросе;
- Маршрутизирует вызовы `send()`, `arg()`, `streamFile()` к этому запросу;
- Эмулирует `chunked`-ответы ESP8266 (накапливает фрагменты и отдаёт одним
  ответом);
- Эмулирует последовательность загрузки файла `UPLOAD_FILE_START` →
  `UPLOAD_FILE_WRITE` → `UPLOAD_FILE_END`.

Это позволяет **одними и теми же файлами** (`StandWebServer.cpp`,
`UpgradeFirm.cpp`, модуль `EspCam`) обслуживать оба варианта сервера.
Переключение — только флаг компиляции.

## Как включить асинхронный вариант

Асинхронный вариант **уже включён по умолчанию** во всех сборках IoTManager
кроме `bk7231n`. То есть ничего делать не нужно — `pio run -e esp32c3m_4mb`
или `pio run -e esp8266_4mb` уже используют асинхронный сервер.

Флаги заданы в `[common_env_data]` файла `platformio.ini`:

```ini
[common_env_data]
build_flags = 
    -DASYNC_WEB_SERVER
    -DASYNC_WEB_SOCKETS
```

И подключаются в каждую env ссылкой `${common_env_data.build_flags}`.

### Как собрать стандартный (синхронный) вариант

Если по какой-то причине нужно собрать синхронный вариант (например,
для отладки — сравнить поведение), достаточно убрать ссылку на
`${common_env_data.build_flags}` из `build_flags` нужного env. Тогда
в `include/Const.h` сработают значения по умолчанию:

```cpp
#if !defined(ASYNC_WEB_SERVER) && !defined(STANDARD_WEB_SERVER)
#define STANDARD_WEB_SERVER
#define STANDARD_WEB_SOCKETS
#endif
```

> ⚠️ **Важно**: раскомментировать `#define ASYNC_WEB_SERVER` в `Const.h`
> **нельзя** — макрос действует во **всех** окружениях включая `bk7231n`,
> где асинхронный вариант запрещён (`#error` в `Const.h`). Асинхронный
> вариант включается **только** флагами `-D` в `platformio.ini`.

## Поддерживаемые платформы

| Платформа | Асинхронный вариант | Синхронный (резервный) |
|---|---|---|
| ESP8266 / ESP8285 | ✅ | ✅ (по умолчанию в `Const.h`) |
| ESP32, ESP32-S2, ESP32-S3, ESP32-C3, ESP32-C6, ESP32-CAM | ✅ | ✅ |
| **BK7231N** (LibreTiny) | ❌ (`#error`) | ✅ (только так) |

Для BK7231N используется кастомная ветка `libretiny` с библиотекой
`LT_WebSockets` — асинхронный вариант не поддерживается и будет
выдавать ошибку компиляции. Это обусловлено особенностями LibreTiny:
`ESPAsyncWebServer` опирается на API, которого нет в этой ветке.

## Цена асинхронного варианта

Асинхронный вариант «дороже» по flash и RAM — это цена за библиотеки
`ESPAsyncWebServer` + `AsyncTCP`/`ESPAsyncTCP`. Замерено на одинаковом
наборе модулей (LittleFS, 4 МБ):

| Сборка `esp8266_4mb` | RAM | Flash |
|---|---|---|
| Стандартный вариант | 38 552 Б (47.1%) | 475 663 Б (45.5%) |
| **Асинхронный вариант** | **38 820 Б (47.4%)** | **496 207 Б (47.5%)** |
| Прирост | +0.3 КБ | **+20.5 КБ** |

Для большинства плат (1 МБ и больше) это не критично — запас остаётся
достаточным. Для плат с 1 МБ flash (например, `esp8266_1mb`) запас
меньше, и рекомендуется проверять `pio run -e esp8266_1mb -t size`
перед прошивкой.

> 📌 **Вывод**: +20 КБ flash за то, что веб-интерфейс больше не
> «замораживает» прошивку — это одна из самых выгодных трат памяти
> в IoTManager.

## Тонкости реализации: что стоит знать разработчику

### 1. Фрагментация больших файлов по RFC 6455

`ESPAsyncWebServer` не умеет отправлять одно сообщение несколькими
фреймами (нет аналога `sendBIN(..., fin, continuation)` из библиотеки
`WebSocketsServer`). Поэтому фреймы формируются **вручную по RFC 6455**:
заголовок, длина, маска (только для клиент → сервер; сервер → клиент
маркировать не нужно). Это позволяет:

- Отправлять файлы больше 50 КБ (лимит одного WS-фрейма для ESP);
- Передавать данные по частям, не загружая весь файл в RAM;
- Поддерживать `fin`/`continuation`-флаги — веб-интерфейс собирает
  файл по `offset` из заголовка первого фрейма.

### 2. Требования к порядку `#include` (ESP8266)

Для ESP8266 асинхронный вариант требует, чтобы блок `#ifdef ASYNC_WEB_SERVER`
в `include/Global.h` подключался **до** `#include <ESP8266WiFi.h>`:

```cpp
#ifdef ASYNC_WEB_SERVER
#include <ESPAsyncWebServer.h>    // включает lwip/tcpbase.h (enum tcp_state)
#include "WebServerCompat.h"
#include "AsyncWebServer.h"
#endif

#ifdef ESP8266
#include <ESP8266WiFi.h>           // объявляет enum wl_tcp_state
// ...
```

Если порядок нарушить, `ESPAsyncWebServer.h` через `lwip/tcpbase.h`
объявит `enum tcp_state` с теми же именами (`CLOSED`, `LISTEN`, …),
что конфликтует с `enum wl_tcp_state` из `wl_definitions.h` esp8266-core:

```
error: 'CLOSED' conflicts with a previous declaration
```

### 3. Колбэк vs loop: почему WS-команды обрабатываются в `loop()`

На ESP8266 колбэк `onWsEvent` выполняется в контексте `loop()` — там
можно сразу обрабатывать команды. На ESP32 коллбэк работает в задаче
`AsyncTCP` (FreeRTOS Task), и **блокировать её нельзя** — иначе
замораживается вся сеть. Поэтому в асинхронном режиме:

- Коллбэк `onWsEvent` только **кладёт сообщение в очередь**
  (8 элементов, кольцевой буфер);
- Сама обработка (`handleWsTextMessage`) выполняется в `loop()` через
  `asyncWebSocketsLoop()`.

Это особенно важно для тяжёлых операций: загрузка файла по `/config|`
или `/profile|`, запись обратных команд (`/gifnoc|`, `/sgnittes|`).

### 4. Ограничение в 3 одновременных WS-клиента

Как и в синхронном варианте, асинхронный сервер обслуживает **не более
3 одновременных веб-клиентов**. Четвёртый отклоняется с ошибкой
`errorsHeapJson["wse1"] = 1`. На практике этого хватает: один браузер
= один клиент, а для просмотра с телефона используется magicIoTm
(которая тоже один клиент).

### 5. Автокоррекция при ошибках `ESPAsyncWebServer`

В коде есть несколько заглушек и `[DEPRECATED]`-блоков, которые
помечены на удаление, но пока сохранены для обратной совместимости:

- `AsyncEventSource events("/events")` — SSE (Server-Sent Events) не
  используется прошивкой, но оставлен для совместимости;
- `sendContent`/`chunkedResponseModeStart` — эмуляция chunked-ответов
  ESP8266WebServer (для `handleFileList`);
- Старый таймаут 3000 мс (`ASYNC_WEB_SOCKETS_SEND_TIMEOUT`) — заменён
  на короткий бюджет 100/200 мс + автоочистка «застрявших» клиентов.

## Влияние на пользователя-разработчика

### ✅ Что стало лучше

1. **Веб-интерфейс больше не «замораживает» прошивку**. Даже если вы
   открыли 5 вкладок с разными устройствами, каждое устройство продолжает
   опрашивать сенсоры, работать с MQTT и выполнять сценарии.

2. **Надёжная OTA и загрузка файлов**. Если во время загрузки `config.json`
   клиент теряет связь, прошивка не зависает на 3 секунды — фрейм
   дропается, клиент закрывается через 2 секунды, и `loop()` продолжает
   работу. Раньше это приводило к «взрыву» событий после дисконнекта.

3. **Множество устройств на одной странице**. magicIoTm и встроенный
   веб-интерфейс могут одновременно держать WS-соединения с несколькими
   устройствами — и каждое устройство обслуживает их без взаимной блокировки.

4. **Меньше проблем с MQTT**. Поскольку `loop()` больше не блокируется,
   MQTT-пинги (`pingreq`/`pingresp`) успевают отправляться регулярно,
   и соединение с брокером стабильнее.

| Клиент отвалился во время передачи | ❌ loop() замёрз на 3 сек | ✅ фрейм дропнулся, клиент закрылся через 2с |
| 3 одновременных браузерные вкладки | ⚠️ очередь, задержки | ✅ параллельно |
| 5 вкладок к 5 разным ESP в одном браузере | ❌ каждая ESP блокирует | ✅ каждая ESP работает независимо |
| ESP32-C3 с ограниченной flash | ✅ (меньше flash) | ✅ (+20 КБ, но влезает) |
| BK7231N | ✅ | ❌ (не поддерживается) |

### ⚠️ Ограничения и компромиссы

- **+20 КБ flash** — для плат с 1 МБ flash (ESP-01, ESP-01S, ESP8285)
  это ощутимо. Проверяйте `pio run -e <env> -t size` перед прошивкой.
- **BK7231N не поддерживает** — асинхронный вариант запрещён (`#error`
  в `Const.h`). BK7231N всегда использует синхронный стек
  (`LT_WebSockets`).
- **Сложность отладки** — асинхронный код через прерывания и коллбэки
  сложнее отлаживать по COM-порту. В `AsyncWebServer.cpp` есть
  debug-флаг `ASYNC_WS_DEBUG`, который можно включить временно:

  ```cpp
  #define ASYNC_WS_DEBUG 1
  ```
    Он выводит в COM-порт все события WS (подключение, отключение,
приём/передачу фреймов, дропы).

## Итог: зачем это знать обычному разработчику

Вы, как разработчик, собираете прошивку IoTManager для своего дома.
Ваша прошивка:

- Опрашивает 10 датчиков температуры каждые 5 секунд;
- Управляет 5 реле по сценариям;
- Подключена к Home Assistant через MQTT;
- И показывает веб-интерфейс на планшете в прихожей.

**До асинхронного веб-сервера**: когда вы открываете веб-интерфейс,
чтобы посмотреть графики, прошивка на 5 секунд перестаёт опрашивать
датчики, MQTT-соединение может упасть (пропуск пинга), а если планшет
вдруг потеряет WiFi — `loop()` замёрзает на 3 секунды, и реле не
реагируют на команды.

**После асинхронного веб-сервера**: веб-интерфейс работает «в фоне».
Датчики опрашиваются ровно каждые 5 секунд, MQTT дышит ровно, реле
реагируют мгновенно, а если планшет отвалится — он закроется через
2 секунды, и ничего не сломается.

Это не теория. Это реальный коммит `f0d80db6` (2026-09-20), который
включил асинхронный вариант во все сборки IoTManager, кроме BK7231N.
Сейчас вы просто собираете прошивку — и асинхронность уже включена.
Никаких настроек не требуется.

### Что делать, если хотите поэкспериментировать

```bash
# Асинхронный вариант (уже включён по умолчанию):
pio run -e esp32c3m_4mb

# Синхронный вариант (резервный): уберите ${common_env_data.build_flags}
# из build_flags env в platformio.ini, либо собирайте bk7231n:
pio run -e bk7231n

# Проверить размер:
pio run -e esp32c3m_4mb -t size
```

Если вы хотите понять, как это работает внутри — читайте исходники:

| Файл | Что искать |
|---|---|
| `include/Const.h` | Флаги `ASYNC_WEB_SERVER`/`STANDARD_WEB_SERVER`, `#error` для BK7231N, таймауты WS |
| `include/Global.h` | `#ifdef ASYNC_WEB_SERVER` — порядок `#include` для ESP8266 |
| `include/WebServerCompat.h` | Класс `AsyncWebServerCompat` — compatibility-слой |
| `include/AsyncWebServer.h` | Интерфейс async WS: слоты, отправка, инициализация |
| `src/AsyncWebServer.cpp` | Реализация: `asyncWebServerInit()`, `asyncWebSocketsLoop()`, `onWsEvent()`, TCP-окно |
| `src/StandWebServer.cpp` | Общие HTTP-обработчики (`/set`, `/status`, `/list`, `/edit`, `/update`) |
| `src/WsServer.cpp` | Общие WS-обработчики (`handleWsTextMessage`, `sendStringToWs`, `sendFileToWsByFrames`) |
| `src/Main.cpp` | `loop()` — вызов `asyncWebSocketsLoop()` вместо `standWebSocket.loop()` |
