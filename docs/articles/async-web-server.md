# Почему IoTManager переходит на ASYNC_WEB_SERVER и ASYNC_WEB_SOCKETS

*Статья для разработчика, который собирает прошивку, правит модули и хочет понять,
что даёт асинхронный сетевой стек на практике — без погружения в тонкости TCP.*

---

## Кратко

Прошивка IoTManager умеет работать с двумя сетевыми стеками:

| Вариант | HTTP (порт 80) | WebSocket (порт 81) | Статус |
|---|---|---|---|
| `STANDARD_WEB_SERVER` + `STANDARD_WEB_SOCKETS` | `WebServer` / `ESP8266WebServer` | `WebSocketsServer` (arduinoWebSockets) | резервный, по умолчанию |
| `ASYNC_WEB_SERVER` + `ASYNC_WEB_SOCKETS` | `ESPAsyncWebServer` | `AsyncWebSocket` | **основной для всех сборок ESP8266/ESP32** |

Асинхронный вариант выбран основным: все окружения в `platformio.ini`
собираются с флагами `-DASYNC_WEB_SERVER -DASYNC_WEB_SOCKETS`
(`platformio.ini`, секция `[common_env_data].build_flags`).
Стандартный стек оставлен как резервный — он включается автоматически,
если ASYNC-флаги не заданы (например, на BK7231N/LIBRETINY, где асинхронные
библиотеки не поддерживаются, см. `include/Const.h`, строки 91–128).

Внешне для пользователя ничего не меняется: тот же веб-интерфейс, тот же
протокол команд, тот же порт 81. Меняется «под капотом» — и меняется
радикально. Ниже — зачем.

---

## 1. В чём проблема синхронного стека

Классический веб-сервер в Arduino (`ESP8266WebServer`, `WebServer` на ESP32)
и библиотека `WebSocketsServer` работают **синхронно**: весь сетевой обмен
происходит внутри `loop()` программы, строка за строкой.

У ESP8266 и одноядерных ESP32 (S2, C3) есть только один поток исполнения
пользовательского кода. Пока ядро в `loop()` отправляет браузеру файл
веб-интерфейса по 1024 байта (`WEB_SOCKETS_FRAME_SIZE`, `include/Const.h:87`)
или ждёт подтверждения TCP, оно не может делать ничего другого:

- **не работают сценарии** `scenario.txt` — таймеры, условия, реакции;
- **не опрашиваются датчики** и не публикуются статусы в MQTT;
- **не обслуживается второй клиент** — открыли веб-интерфейс с телефона,
  пока с ноутбука идёт загрузка страницы, и телефон ждёт;
- хуже того, **прошивка может подвиснуть на секунды**. Если браузерный
  клиент потерял WiFi (ушёл за стену, ноутбук уснул), TCP-соединение
  остаётся «полуоткрытым». Синхронная запись в такое соединение ждёт
  таймауты стека (`select`-таймаут × повторы записи) — и `loop()`
  замирает. В коде это описано буквально: «Синхронная запись
  (WiFiClient::write) в клиента, потерявшего WiFi, блокирует loop()
  на секунды (select-таймаут × write-retry), замораживая таймеры и
  сценарии — особенно заметно на одноядерном ESP32-S2»
  (`src/WsServer.cpp:449-454`). После возврата из такой блокировки
  прошивка «наверстывает» пропущенное лавиной событий — это те самые
  странные «взрывы» в логе.

Для устройства умного дома это критично: реле, которое должно щёлкнуть
по сценарию через 100 мс, щёлкает через 3 секунды — или устройство
перезагружается по сторожевому таймеру (watchdog).

## 2. Что значит «асинхронный» простыми словами

В асинхронном стеке (библиотеки `ESPAsyncWebServer` + `AsyncTCP`/`ESPAsyncTCP`)
всё сетевое ввод-вывод выполняется **событием, а не ожиданием**:

- TCP-стек работает в своей задаче (на ESP32) или в обработчиках прерываний
  событий (на ESP8266), а не внутри `loop()`;
- данные отправляются и принимаются **в фоне**, между вызовами `loop()`;
- `loop()` получает только готовые события: «пришёл запрос», «сообщение
  собрано целиком», «клиент подключился/отключился».

Программа перестаёт ждать сеть. Сеть ждать её не заставляет.

Протокол веб-интерфейса при этом **не изменился**: команды те же
(`/pi|`, `/params|`, `/config|`, бинарные фреймы с файлами), порт тот же
(81), максимум клиентов тот же (3). Поэтому веб-интерфейс, мобильное
приложение и панель magicIoTm работают с обеими реализациями без правок.
Общий обработчик команд `handleWsTextMessage()` один на оба стека
(`src/WsServer.cpp:82-88`).

## 3. Плюсы ASYNC_WEB_SERVER (HTTP)

### 3.1. Страница грузится, пока устройство живёт

Открытие веб-интерфейса в браузере — это десятки HTTP-запросов
(HTML, CSS, JS, шрифты). У синхронного сервера каждый запрос
обслуживается до конца, и пока идёт отдача большого файла, сценарии
встают. Асинхронный сервер отдаёт файлы фоновой задачей: `loop()`
свободен, сценарии идут, статусы публикуются. Браузер получает страницу
не «вместо» работы устройства, а «параллельно» с ней.

### 3.2. Отдача файлов без загрузки в оперативную память

Ответ умеет читать файл из LittleFS **позже, частями**, из задачи TCP:
файл открывается по пути и читается тогда, когда освобождается
TCP-окно, а не копируется целиком в RAM перед отправкой
(`src/AsyncWebServer.cpp:253-279`). На устройствах с 40–80 КБ свободной
кучи это спасает от перезагрузок по нехватке памяти при отдаче больших
файлов.

### 3.3. Загрузка файлов на устройство (upload) по частям

Загрузка конфигурации или прошивки по HTTP приходит фрагментами, и
каждый фрагмент передаётся обработчику сразу (`UPLOAD_FILE_START →
WRITE → END` эмулируется поверх асинхронных колбэков,
`src/AsyncWebServer.cpp:34-56`). Файл пишется на флеш по мере поступления,
не накапливаясь в памяти.

### 3.4. Единый код обработчиков

Обёртка `AsyncWebServerCompat` повторяет интерфейс синхронного сервера
(`HTTP.hasArg()`, `HTTP.arg()`, `HTTP.streamFile()`, …), поэтому
все маршруты (`/set`, `/status`, `/list`, `/edit`, `/update`, OTA, CORS)
зарегистрированы один раз в общем коде `StandWebServer.cpp` и работают
в обеих сборках (`src/AsyncWebServer.cpp:1-2, 322-326`,
`include/WebServerCompat.h`). Для разработчика модуля это значит:
**правите обработчик один раз — работает он в обоих вариантах**.

## 4. Плюсы ASYNC_WEB_SOCKETS (WebSocket)

Веб-сокеты — это основной канал: через них живёт дашборд, конфигуратор,
обновления. Именно здесь синхронный стек болел больше всего.

### 4.1. Бюджет отправки вместо секундного зависания

Раньше при отправке фрейма «мёртвому» клиенту прошивка синхронно ждала
освобождения TCP-окна до 3 секунд (`ASYNC_WEB_SOCKETS_SEND_TIMEOUT`,
помечен как `[DEPRECATED]` в `include/Const.h:130-135`). Теперь на фрейм
выделяется короткий бюджет — **100 мс** для статусов и **200 мс** для
фреймов файлов (`ASYNC_WEB_SOCKETS_SEND_BUDGET_MS`,
`ASYNC_WEB_SOCKETS_SEND_BUDGET_FILES_MS`,
`include/Const.h:137-146`). Не уложился — фрейм дропается, а клиент
помечается «застрявшим».

Эффект: одно засыпание ноутбука с открытым дашбордом больше не
замораживает всё устройство на секунды.

### 4.2. Автозакрытие «застрявших» клиентов

Клиент, который не подтверждает приём дольше 2 секунд
(`ASYNC_WEB_SOCKETS_STUCK_CLOSE_MS`), принудительно отключается
(`asyncWebSocketsLoop()`, `src/AsyncWebServer.cpp:661-688`). Слот
освобождается, бюджет отправки больше не тратится впустую. При этом
есть защита от ложных срабатываний: если клиент продолжает **присылать**
данные (веб-интерфейс шлёт `/pi|` каждые ~2 секунды), он жив — метка
«застрявшего» снимается, соединение не рвётся
(`src/AsyncWebServer.cpp:672-679`).

### 4.3. Потоковая отправка файлов без сборки в памяти

Большие файлы (`items.json`, `config.json`, графики) отправляются
фрагментами по RFC 6455 — библиотека `ESPAsyncWebServer` умеет
единый интерфейс, но не умеет фрагментированные сообщения, поэтому
фреймы формируются вручную (`src/AsyncWebServer.cpp:436-549`).
Важно для разработчика: **файл любого размера не собирается целиком
в оперативной памяти** — буфер одного фрейма (1024 байта), читается
очередной кусок из файла, уходит в сокет, следующий. Пиковое
потребление RAM не зависит от размера файла.

### 4.4. Очередь входящих команд

Веб-интерфейс шлёт несколько команд одним TCP-пакетом (`/devlist|` и
`/|` приходят за одну миллисекунду). В асинхронном варианте собранные
сообщения ставятся в очередь из 8 слотов и обрабатываются в `loop()`
(`src/AsyncWebServer.cpp:361-371, 690-702`). Ничего не теряется,
а обработка выполняется в контексте `loop()` — это упрощает модули:
команда всегда обрабатывается там же, где и раньше.

Обработка в `loop()` осознанная: на ESP32 колбэки `AsyncTCP` работают
в отдельной задаче, а обработка команд блокирующая (отправка файлов
фреймами) — выполнять её в задаче TCP было бы опасно. На ESP8266
колбэки и так выполняются в контексте `loop()`, так что порядок
сохраняется для обеих плат.

## 5. Что это даёт рядовому разработчику на практике

1. **Сценарии отрабатывают вовремя.** Таймер «выключить свет через 5 минут»
   не сдвинется на несколько секунд, потому что кто-то открыл веб-интерфейс.

2. **Устройство не перезагружается само.** Меньше блокировок `loop()` —
   меньше срабатываний сторожевого таймера; меньше пиковых аллокаций —
   меньше нехватки кучи.

3. **Стабильность при «грязной» сети.** Клиент, потерявший WiFi,
   изолируется и отключается сам, не тянет за собой всё устройство.

4. **Предсказуемая задержка.** Максимальная пауза `loop()` при сетевой
   нагрузке измеряется миллисекундами (бюджет фрейма), а не секундами
   (TCP-таймаут).

5. **Меньше кода в модулях.** Транспорт абстрагирован: `sendStringToWs()`,
   `sendFileToWsByFrames()`, `webSocketSendBin()` — одинаковые вызовы
   для обоих стеков (`src/WsServer.cpp:431-492`). Модуль не знает,
   какой стек скомпилирован.

6. **Понятная диагностика.** Временный отладочный лог WS включается
   одним макросом `ASYNC_WS_DEBUG` (`src/AsyncWebServer.cpp:6-12`):
   видно каждый фрейм, дроп и причину («stuck client», «canSend»).

## 6. Как это включить и проверить

- **По умолчанию всё уже включено**: флаги `-DASYNC_WEB_SERVER
  -DASYNC_WEB_SOCKETS` стоят в `[common_env_data].build_flags` файла
  `platformio.ini` (строки 11–12), на них ссылаются все базовые env плат.
- **Резервный вариант** включается удалением этих двух флагов из
  сборки — тогда сработают дефолты `STANDARD_*` (`include/Const.h:106-109`).
- **Нельзя миксовать**: оба сервера занимают порт 80, оба варианта
  сокетов — порт 81; недопустимые сочетания отсекаются на этапе
  компиляции с понятным `#error` (`include/Const.h:116-128`).
- **BK7231N (LIBRETINY) не поддерживает** асинхронный стек — для него
  остаётся только стандартный вариант (`LT_WebSockets`).
- Сборка асинхронного варианта требует библиотек `ESPAsyncWebServer` и
  `AsyncTCP` (на ESP8266 — `ESPAsyncTCP`) в `lib_deps` окружения
  (`include/Const.h:92-96`).

## 7. Ограничения и подводные камни

Честности ради — асинхронность не бесплатна:

1. **Контекст выполнения колбэков.** На ESP32 сетевые колбэки работают
   в задаче `AsyncTCP`, а обработка команд — в `loop()`. Разделяемое
   состояние между ними нужно защищать критическими секциями
   (комментарий `src/AsyncWebServer.cpp:362-364`). При переносе кода
   из стандартного стека не вызывайте из колбэков ничего тяжёлого.

2. **Дропы фреймов — норма.** Статусы волатильны: если клиент не
   успевает, фрейм просто теряется, и это осознанное решение
   (повторная отправка устаревшего статуса бессмысленна). Если ваш
   модуль шлёт критичные данные по WS — закладывайте подтверждение
   на уровне протокола, а не полагайтесь на доставку каждого фрейма.

3. **Ручная фрагментация WS.** Часть протокола пришлось писать руками
   (фреймы RFC 6455), потому что готового API фрагментированной
   отправки в библиотеке нет (`src/AsyncWebServer.cpp:436-441`).
   При обновлении библиотеки это место стоит перепроверять.

4. **Память TCP-буферов.** Асинхронный стек держит свои буферы на
   каждое соединение; лимит в 3 клиента (`src/AsyncWebServer.cpp:710-716`)
   частично и про это. Резко поднимать число клиентов без оценки кучи
   не стоит.

## 8. Итог

Переход на `ASYNC_WEB_SERVER` + `ASYNC_WEB_SOCKETS` решает главную
болезнь синхронного стека — **блокировку всей прошивки одним сетевым
клиентом**. Устройство перестаёт зависать, когда браузер засыпает
или сеть деградирует; сценарии и опрос датчиков идут параллельно с
отдачей веб-интерфейса; пиковое потребление оперативной памяти перестаёт
зависеть от размера передаваемых файлов. При этом протокол веб-интерфейса,
обработчики команд и порты не меняются — модули и внешние инструменты
(magicIoTm, мобильное приложение) продолжают работать как раньше.

Для разработчика рекомендация простая: **собирайте новые модули и
проверяйте поведение на ASYNC-варианте** — это основной путь проекта;
стандартный стек держите в уме только как запасной для платформ, где
асинхронные библиотеки недоступны (BK7231N).
