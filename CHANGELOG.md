# Changelog

Все заметные изменения репозитория IoTManager.
Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/).
Полная история: `git log --oneline`.

## [2026-09-21]

### Прошивка

- Автоматический счётчик в версии прошивки. `FIRMWARE_VERSION` в `include/Const.h` теперь
  строка вида `"463.2225"` — `<ручная часть>.<число коммитов git>`: первое число поднимается
  вручную при значимых изменениях, второе при каждой сборке прошивки перезаписывает новый
  pre-скрипт `tools/version_bump.py` (`git rev-list --count HEAD`). Скрипт подключён через
  `extra_scripts` во все окружения `platformio.ini`, включая те, что переопределяют
  `extra_scripts` (esp32-сборки, `esp8266_16mb`, `bk7231n`). На таргетах без компиляции
  прошивки (`buildfs`, `uploadfs`, `uploadfsota`, `size`) и при недоступном git версия
  остаётся прежней; старый целочисленный формат (`#define FIRMWARE_VERSION 463`) скрипт
  мигрирует сам. Правка строки идёт на уровне байтов — кодировка и CRLF файла не
  затрагиваются. Все места использования работают со строкой через
  `String(FIRMWARE_VERSION)`; в списке устройств поле `fv` теперь строка (`jsonWriteStr_`,
  `src/DeviceList.cpp`). Следствие: после каждого коммита счётчик устаревает, и следующая
  сборка снова меняет строку в `Const.h` (файл будет «грязным» в git) — это ожидаемо;
  изменённый `Const.h` можно коммитить вместе с работой.

### Прошивка

- Добавлен асинхронный вариант веб-сервера и веб-сокетов: `ASYNC_WEB_SERVER` +
  `ASYNC_WEB_SOCKETS` (ESPAsyncWebServer 3.12.x + AsyncTCP/ESPAsyncTCP) как альтернатива
  стандартному `STANDARD_WEB_SERVER` + `STANDARD_WEB_SOCKETS` (WebServer/ESP8266WebServer +
  WebSocketsServer). Отдельных окружений `*_async` в `platformio.ini` нет: асинхронный
  вариант включён сразу во всех сборках через `[common_env_data]` — в `lib_deps_external`
  добавлен `ESP32Async/ESPAsyncWebServer`, а `build_flags` задаёт
  `-DASYNC_WEB_SERVER -DASYNC_WEB_SOCKETS`; на `${common_env_data.build_flags}` ссылаются
  все 18 базовых env плат, ESP8266-окружения дополнительно тянут `ESP32Async/ESPAsyncTCP`
  в `lib_deps`. `bk7231n` не затронут: его `build_flags` на
  `${common_env_data.build_flags}` не ссылается, там остаются `STANDARD_WEB_SERVER` +
  `STANDARD_WEB_SOCKETS` (LT_WebSockets). Стандартный вариант сохранён в коде как
  резервный: значения по умолчанию ниже в `Const.h` срабатывают, только если не задан ни
  один ASYNC-флаг (готовые env его так не собирают). Взаимные исключения и запрет для
  bk7231n (LIBRETINY) проверяются в `Const.h`. Вариант нельзя включать через `#define` в
  `Const.h` — макрос действует во всех окружениях, в том числе в bk7231n, где он запрещён
  (`#error`), и лишает возможности собрать стандартный вариант без правки кода.
  Обработчики HTTP общие для обоих вариантов (`StandWebServer.cpp`,
  `UpgradeFirm.cpp`): в асинхронной сборке синхронный интерфейс (`HTTP.on/send/arg/...`)
  имитирует обёртка `AsyncWebServerCompat` (`include/WebServerCompat.h`). Веб-сокеты —
  тот же протокол и порт 81; файлы уходят фреймами по RFC 6455, приём WS-команд выполняется
  в `loop()` (колбэк AsyncTCP блокировать нельзя). `getContentType` и `streamFile`
  (включая отдачу `*.gz` с `Content-Encoding: gzip`) работают одинаково в обоих вариантах.
  Для ESP8266 блок ASYNC-заголовков в `include/Global.h` подключается до `ESP8266WiFi.h`:
  иначе `lwip/tcpbase.h` (из `ESPAsyncWebServer.h`) конфликтует с `enum wl_tcp_state` из
  `wl_definitions.h` (`error: 'CLOSED' conflicts with a previous declaration`).
  Проверено сборкой: `esp8266_4mb` 475 663 Б flash / 38 552 Б RAM в стандартном варианте
  против 496 207 Б flash / 38 820 Б RAM в асинхронном (прирост ~20 КБ flash) — сравнение
  снималось на временном окружении `esp8266_4mb_async`, которое в `platformio.ini` не
  сохранено (сейчас ASYNC-флаги включены у всех env через `[common_env_data]`);
  проверялись также `esp32s2_4mb` и модуль `EspCam` в обоих вариантах.
- **ESP32-C3 (`esp32c3m_4mb`): `board_build.flash_mode = dio` — иначе паника загрузки.**
  Плата `lolin_c3_mini` объявляет `build.flash_mode = qio`, поэтому Arduino-сборка берёт
  набор предкомпилированного SDK/библиотек `tools/sdk/esp32c3/qio_qspi`
  (`CONFIG_ESPTOOLPY_FLASHMODE_QIO`), тогда как PlatformIO принудительно пишет образ и
  загрузчик в режиме `dio` (`_get_board_flash_mode` в `builder/main.py` заменяет
  `qio`/`qout` на `dio`), а каталог SDK выбирается как `build.flash_mode + "_qspi"`
  (`tools/platformio-build-esp32c3.py`). На железе это выглядит как паника
  `assert failed: do_core_init startup.c:328 (flash_ret == ESP_OK)` — падает
  `esp_flash_init()` в приложении (плюс `Core dump flash config is corrupted`).
  С этой опцией вариант SDK становится `tools/sdk/esp32c3/dio_qspi` и совпадает с режимом
  образа; проверено сборкой `esp32c3m_4mb` (141 файл, Flash 70.8 %) и заголовками
  `firmware.bin`/`bootloader.bin` (`02 2f` = DIO, 4MB, 80 MHz).
  После смены режима прошивать с полным стиранием: `-t erase`, затем `-t upload` и `-t uploadfs`
  (при `erase` файловая система LittleFS стирается).
- Удалено отладочное окружение `esp32c6_4mb_debug` из `platformio.ini` (не использовалось).
  Отладочная сборка ESP32-C6 при необходимости делается копией `esp32c6_4mb` с
  `build_type = debug` и `-DCORE_DEBUG_LEVEL=4`. Ссылок на
  `${common_env_data.build_flags}` стало 18.
- Версия прошивки поднята: `FIRMWARE_VERSION 463` (`include/Const.h`).
- Ветка `tools` объединена с `ver4dev` (97 коммитов, merge-base `80d112f2`):
  - код панели `tools/magicIoTm/` и `tools/measure_size/` включён в репозиторий
    (раньше был только локальным); мусор (`__pycache__`, логи замеров) в индекс
    не взят;
  - из прошивки перенесены OTA-фичи: WS-команды `/update1|` (только прошивка) и
    `/update2|` (только ФС) в `src/WsServer.cpp`, параметр `type` у локальной OTA
    (`/api`-обработчик `handleLocalOTA_Handler` в `src/StandWebServer.cpp`);
  - `modinfo.json` модуля `EctoControlAdapter` оставлен в редакции ver4dev (v2.0,
    с `usedRam`) — в `tools` параллельно набиралась другая редакция метаданных
    (v1.0), код модуля при этом не менялся;
  - генерируемые артефакты `data_svelte/*` и `src/modules/API.cpp` сняты с учёта
    (их пересобирает `PrepareProject.py`, наборы-источники `data_full/` и
    `data_lite/` остаются в репозитории);
  - `AGENTS.md`, `KODA.md`, `README.md`, `docs/` в `ver4dev` остаются локальными
    (решение от коммита `3d0c233f`), `.gitignore` объединён (полный список
    runtime-игноров из `tools` + блок локальных документов).
- Репозиторный `platformio.ini` синхронизирован с эталонным профилем:
  `default_envs = esp32c3m_4mb`; в `esp32c3m_4mb_fromitems` актуализирован набор модулей
  (добавлены `sensors/AnalogAdc`, `sensors/Ds18b20` + `DallasTemperature`,
  `exec/ButtonIn`/`ButtonOut`; убраны `Cron`, `owmWeather`, `VariableColor`); убран
  пустой `build_flags` в `esp32c6_8mb_fromitems`.

### Панель magicIoTm

- WS-клиент панели отвечает Pong на Ping устройства (RFC 6455): во все циклы
  приёма (`fetch_ram`, `fetch_ram_file`, `fetch_profile`, `fetch_settings`)
  добавлен ответ pong-фреймом с эхом payload пинга.
- Редакторы файлов защищены от потери несохранённых правок. Правки отслеживаются
  во всех трёх редакторах (RAM и FS устройства, FS проекта); у имени файла в
  заголовке редактора появляется индикатор «●». При переходе к другому файлу,
  другому устройству, другому проекту или при выходе из устройства, а также при
  «⤵ Получить этот файл» (полученный файл затирает содержимое редактора) показывается
  модалка «Сохранить / Не сохранять / Отмена»; при неудачном сохранении переход не
  выполняется. Автовосстановление последнего выбранного файла (при возврате на
  устройство/проект и обновлении деревьев) больше не затирает «грязный» редактор.
  Закрытие/обновление страницы с правками подтверждается нативным окном браузера.
  Попутно исправлено: при открытии проекта состояние редактора FS предыдущего
  проекта не сбрасывалось — устаревший путь мог попасть в «⤵ Получить этот файл».
- Перед получением файлов с устройства кнопками **«⤵ Получить файлы»** и
  **«⤵ Получить этот файл»** для устройств со статусом «не в сети» сначала
  выполняется пинг: ответил — получение продолжается (статус локально
  меняется на «в сети»), нет — предупреждение «Устройство … не в сети
  (ping не отвечает)» вместо долгого ожидания WS/HTTP-таймаута. Источник
  «с устройства» в модалке проекта тоже предварительно пингуется (статус
  «в сети» мог устареть). Новый эндпоинт `POST /api/device/<key>/ping`
  (ICMP через `_host_pingable`, FSM-статус не меняет).
- В разделе «📌 Проверка переменных в config.json» расширенной проверки
  scenario.txt ненайденные переменные теперь показываются с номерами строк,
  где они используются в сценарии: «`имя` — используется на стр. 4, 12».
  Добавлена функция `extractScenarioVarLines` (карта «имя → строки») в
  `static/index.html`.
- Кнопка **«💾 Сохранить»** в менеджере устройства теперь сохраняет файл и
  локально, и на устройство (если оно «в сети»), а не одно из двух: раньше
  в разделе RAM при недоступном устройстве сохранение падало целиком, а в FS
  писала только на диск. Итог отражается в сообщении: «Сохранено локально и
  в устройство», «Сохранено локально, устройство не доступно», «Сохранено
  локально, ошибка записи в устройство: …». В разделе RAM кнопка включена для
  всех текстовых файлов (локально правится любой), запись на устройство — только
  для поддерживаемых прошивкой (`config.json`, `scenario.txt`, `settings.json`,
  `layout.json`, `devlist.json`); для остальных и для FS-файлов — «Сохранено
  локально». Старая функция `pushFile` помечена `[DEPRECATED]`.
- Исправлено периодическое сбрасывание верхних индикаторов FLASH/RAM/FS (gauge)
  в 0 после завершения «⚖️ Замер базы» (и других замеров): кэши modinfo и
  platforms перечитывались с диска через `clear()` + медленное заполнение, и
  параллельный запрос `/api/size` мог попасть в пустое окно (`total_flash` = 0 →
  0 %). Теперь оба кэша заполняются в локальный словарь и подменяются целиком
  (`core/config.py`), а `POST /api/modules/reload` перечитывает и platforms.json
  тоже — раньше он обновлял только modinfo, а перезагрузка platforms в
  SSE-потоке замера часто не выполнялась, потому что клиент закрывает поток
  сразу после события `done`.
- Лимит длины имени устройства увеличен с 16 до 64 символов (подсказка при вводе
  в `index.html` и серверная валидация `validate_name` в `utils/projects.py`);
  прошивка ограничения не имеет. Код устройства: имя читается в динамический
  `String nameId` и используется в MQTT-топике last-will.
- Кнопка **«⧉ Копировать»** у устройства в списке (рядом с «✕»): копирует
  устройство в проект — существующий (выбор категории и проекта) или новый
  (создаётся из корневого шаблона `myProfile.json`). Источник — сохранённые
  файлы RAM или FS устройства; правила те же, что у кнопок «⤵ Из устройства»
  в панели проекта: `settings.json` → `iotmSettings` (все поля кроме id/ip/root),
  `profile.json`/`flashProfile.json` → платформа из `default_envs`
  (несовместимые модули отключаются) и активность модулей по `path`.
  Если раздел FS устройства локально пуст (нет сохранённых файлов) и устройство
  в сети, панель сначала предлагает скачать раздел FS на диск (с прогрессом,
  как в менеджере устройства), затем продолжить копирование; без сети —
  предупреждение и продолжение с тем, что сохранено.
  Если целевой проект открыт в панели, панель перезагружается. Новый API:
  `POST /api/device/<key>/copy-to-project` (`{dst_cat, dst_name, section}`).
- Кнопки **«+»** рядом с селектами в модалках: «Копировать устройство в проект»
  (у селектов «В категорию:» и «Проект:»), «Копировать проект», «Перенести
  проект» (у «В категорию:») и «Новый проект» (у «Категория:»). Действия — как
  у кнопок сайдбара «+ Категория»/«+ Проект»: открывается соответствующая
  модалка создания, после чего происходит возврат в исходную модалку с выбранным
  новым пунктом (введённые в поля значения сохраняются). Пункт «➕ Новый проект…»
  из модалки копирования устройства удалён — проект создаётся по «+».
- Исправлено переименование проекта/категории сменой только регистра букв
  (например `MyProject` → `myproject`): на Windows ФС нечувствительна к регистру,
  проверка «уже существует» ложно срабатывала на тот же самый каталог. Теперь
  совпадение с исходным каталогом (`os.path.samefile`) разрешено — то же для
  переноса проекта в ту же категорию со сменой регистра; конфликт с другим
  проектом по-прежнему блокируется (`utils/projects.py`).
- Оптимизация пинга устройств: узлы вне локальных подсетей панели (панель
  переехала в другую сеть) больше не пингуются каждую минуту — подсети
  интерфейсов определяются по psutil (кэш 30 сек), чужой узел сразу считается
  недоступным для FSM, полный пинг выполняется раз в 10 минут
  (`CROSS_SUBNET_RETRY`) на случай доступности по маршруту (VPN). Если psutil
  недоступен, поведение прежнее.
- Кнопка **«⤵ Получить этот файл»** в панели «Файлы из файловой системы» устройства:
  скачивает с устройства только выбранный в дереве файл (RAM — по WS, FS — по HTTP)
  без полной выгрузки раздела. Новый API: `POST /api/device/<key>/fetch/<ram|fs>/file`.
- В разделе **«Файловая система FS» проекта** появились кнопки «⤵ Получить этот файл»
  и «⤵ Получить файлы» с модалкой выбора источника: устройство/RAM (сохранённые),
  устройство/FS (сохранённые), устройство/RAM (с устройства), устройство/FS
  (с устройства). Пункт не показывается, если источник недоступен: нет сохранённого
  файла(ов) — не показываются «сохранённые» пункты; нет устройств в сети — не
  показываются пункты «с устройства»; «RAM — с устройства» показывается только для
  файлов, которые прошивка отдаёт по WS (набор RAM: `config.json`, `items.json`,
  `widgets.json`, `scenario.txt`, `settings.json`, `ota.json`, `profile.json`),
  для остальных (например `flashProfile.json`) остаётся только сохранённая копия;
  при полном отсутствии источников выводится сообщение. Новые API:
  `GET /api/projects/<cat>/<name>/file/sources`,
  `POST /api/projects/<cat>/<name>/file/from-device`.
- Кнопки в шапках панелей файлов (RAM/FS устройства и «Файловая система FS»
  проекта) прижаты друг к другу у правого края: `margin-left:auto` в
  `.devmgr-panel-head` применяется только к первой кнопке группы, а не к каждой —
  раньше свободное место делилось между кнопками и они растягивались по шапке.
- Исправлено отображение бинарных файлов (`*.gz`, `favicon.ico`) в редакторах:
  при выборе бинарного файла в слое подсветки оставался подсвеченный текст
  предыдущего файла — слой теперь очищается, в редакторе виден только
  плейсхолдер «Бинарный файл — просмотр и редактирование недоступны».
- Бинарные файлы можно получать с устройства: путь выбранного бинарного файла
  больше не сбрасывается, поэтому «⤵ Получить этот файл» (панель устройства
  и модалка проекта «RAM/FS — с устройства»/«… — сохранённые») работает и для
  них. Запись бинарных файлов из редактора дополнительно заблокирована на
  бэкенде `POST /api/device/<key>/file/<section>` (как в проектном эндпоинте),
  кнопки «💾 Сохранить»/«💾 На устройство» игнорируют бинарный файл.
- Проверка `scenario.txt` запускается только кнопкой «🔍 Проверка» (всегда заново). Результат запоминается в кэше сессии отдельно для каждого `scenario.txt` каждого устройства/проекта: при возврате к файлу панель «🔍 Проверка» показывается автоматически с сохранённым результатом. Закрытие панели кнопкой ✕ очищает кэш этого сценария (этого устройства/проекта) — до новой проверки панель автоматически не показывается.
- Секция «🗂️ Файловая система FS» на странице проекта имеет фиксированную высоту: длинные результаты проверки не растягивают её по вертикали, тело проверки прокручивается внутри.
- Исправлена рассинхронизация подсветки/выделения в редакторе при прокрутке в самый низ: слой подсветки повторяет клиентскую область textarea (без полос прокрутки), поэтому максимумы прокрутки совпадают и слой больше не «упирается» в свой предел раньше textarea; размер слоя обновляется и при прокрутке — появление/исчезновение полосы не даёт скачка и рассинхрона выделения со строками.
- Исправлено отставание цветной подсветки на одну строку в конце файлов, оканчивающихся на `\n`: textarea рисует завершающий перенос как пустую строку, а `<pre>` — нет; в слой подсветки добавляется компенсирующий перенос, поэтому подсветка, номера строк и выделение сходятся до последней строки.
- Номера строк в редакторе сценария теперь рисуются слоем поверх текста (вместо отдельной колонки слева): слой не участвует в выделении и прокрутке, текст редактора сдвигается вправо только пока номера показаны.
- В разделе «🗂️ Файловая система FS» выбранный файл запоминается на сессию отдельно для каждого устройства/проекта: при переходе на другое устройство или проект и возврате файл выбирается автоматически.
- Расширенная проверка `scenario.txt` (🔍 Проверка) больше не требует выбранного
  устройства: сохранённый `config.json` берётся с диска панели (RAM/FS папка
  устройства или `data_svelte` проекта), а не «с устройства». Ключ папки
  запоминается при открытии файла; если сохранённый `config.json` рядом со
  `scenario.txt` не найден — проверка переменных честно сообщает об этом вместо
  ошибки «Устройство не выбрано».
- `fix(magicIoTm)`: в проверке переменных `scenario.txt` ID элементов `config.json`
  сравнивались со списком объектов, из‑за чего все переменные ложно считались
  неизвестными; теперь сопоставляются строковые `id`.
- В панели проекта ниже «📝 Описание проекта» появился раздел **«Файловая система
  FS»**: дерево и редактор файлов `data_svelte` проекта (как в менеджере устройств,
  но без кнопки «⤵ Получить файлы»; «💾 Сохранить» пишет файл локально в проект).
  Новые API: `GET /api/projects/<cat>/<name>/tree/fs`, `GET|POST
  /api/projects/<cat>/<name>/file/fs`.
- Бинарные файлы (`*.gz`, `favicon.ico`) в дереве «Файлы из файловой системы»
  (и в менеджере устройств, и в разделе FS проекта) видны, но их содержимое
  в редакторе не открывается — показываются только имя и размер; редактирование
  и сохранение недоступны. Чтение содержимого бинарников на сервере запрещено,
  `?meta=1` возвращает только метаданные.
- В списке модулей подсвечивается статус размера: красная строка — ошибка
  компиляции («Ошибка компиляции для этой платформы» / «Не компилируется для
  всех платформ»), жёлтая — «Размер не замерялся». Статус считается по
  `sizeInfo.usedFLASH` в `modinfo.json` и отдаётся в `/api/modules/compatibility`
  полем `sizeState` (`ok` / `error_platform` / `error_all` / `missing`).
- Исправлено «ESP-устройство не обнаружено» для плат с нативным USB
  (ESP32-S2/S3/C3): `esptool flash_id` на портe приложения (например COM6)
  сбрасывает чип в режим загрузки с переименованием порта (COM6 -> COM7), из‑за
  чего `detect_device` падал с `OSError(22, 'Invalid argument')`. Теперь после
  неудачи ищем переименованный COM‑порт того же USB‑устройства (по
  VID/serial_number/location) и повторяем `flash_id`. Важно: результатом
  возвращается ИСХОДНЫЙ порт приложения (COM6), а не загрузчика (COM7) — иначе
  PlatformIO при загрузке сбрасывает чип обратно в приложение и не может
  отследить переименование COM7→COM6 на Windows. `list_esp_ports` и
  `list_raw_ports` делают повторный опрос при пустом результате. Сообщение об
  ошибке уточнено (разные причины: порт не создаётся / чип не отвечает / семейство
  не совпадает).
- Исправлен `NameError: name 'flash_start' is not defined` в
  `routes/upload.py`: функция запуска прошивки называется `start` (из
  `core.flasher`) и не была импортирована — добавлен импорт `start as flash_start`.
- Исправлен сбой прошивки файловой системы (`pio run -t uploadfs`) с
  `warning: can't read source directory` и `*** [.pio\build\<env>\littlefs.bin] Error 1`:
  причина — устаревший путь `[platformio] data_dir` в `platformio.ini` проекта после
  переименования категории (`Test` → `Платы`) или переноса проекта; PlatformIO берёт
  этот путь как `$PROJECT_DATA_DIR` и передаёт его `mklittlefs -c`. Теперь:
  - `utils/projects.py` умеет читать/перезаписывать `data_dir` (только строку в секции
    `[platformio]`, остальной ini и комментарии не трогаются) и автоматически
    синхронизирует его при переименовании категории/проекта, переносе и копировании;
  - перед USB-прошивкой в режимах `fs`/`full` каталог данных сверяется с проектом:
    `POST /upload/start` возвращает `409` с `code: "data_dir"`, а UI показывает модалку
    «Исправить и прошить» (`POST /projects/repair-data-dir`) с повторным запуском;
  - `utils/flash.py` дополнительно проверяет каталог в воркере (понятная ошибка вместо
    «код 1») и после успешной прошивки обновляет `firmware.bin`/`littlefs.bin`
    в `iotm/<платформа>/400/` проекта.
- Добавлены тесты панели `tools/magicIoTm/tests/test_data_dir.py`
  (`cd tools/magicIoTm && python -m unittest discover -s tests -v`; pytest тоже
  подходит): проверяются чтение/запись `data_dir`, предпроверка перед прошивкой и
  API починки `platformio.ini`. Сеть, PlatformIO и устройство не нужны. Заодно
  `compile_commands.json` добавлен в `.gitignore`, а `fix_data_dir` больше не падает
  `ValueError`, если проект и корень репозитория лежат на разных дисках (пишется
